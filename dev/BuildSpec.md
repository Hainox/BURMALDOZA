# Build Specification — Бурмалдоза, skeleton v0.1

## Дополнение #105 — утверждено владельцем 14.10.2026

- Денежные поля `wallets.balance`, `ledger_entries.amount_delta/balance_after`,
  `game_players.stack`, `game_rounds.bet_amount/payout_amount` переводятся на BIGINT

- Downgrade не обрезает суммы: при выходе за INTEGER операция полностью отклоняется.

- Приёмка: реальная выплата siege-2 ×72 при ставке 1 000 000 поверх баланса
  2 100 000 000, durable replay, конкуренция ставок до баланса, отказ DOUBLE без
  средств; миграция вверх/вниз с сохранением данных и отказом небезопасного downgrade;
  browser-проверка ceiling. Исправления — отдельный PR, без server deploy/merge.

**Статус:** технический skeleton собран; финальные тематические ассеты, лимиты и публичный запуск требуют отдельной приёмки.

## Goal

Запустить Telegram-бота и Mini App «Бурмалдоза» для сообщества Memendoza: серверно подтверждаемая виртуальная экономика и три игровые комнаты с ясной, живой анимацией.

## Approved rooms

| Комната | Правила | Статус foundation |
| --- | --- | --- |
| 3×7 Slot | Три барабана, семь видимых рядов, paylines и integer payout | domain + Monte Carlo + Mini App skeleton |
| Blackjack GFL | Hit / Stand / Double, dealer resolution, integer-safe payout | domain + Monte Carlo + Mini App skeleton |
| Heads-up Hold’em / RGG Poker | Два места, один pot, Fold / Check / Call / Raise | domain + equity simulation + Mini App skeleton |

Итог раунда рассчитывает сервер. Клиент отправляет intent, получает подтверждённый snapshot/event и лишь затем проигрывает соответствующую фазу движения.

### Slot v2 — обязательный motion-контур

- `SlotOutcome`/room event содержит финальную сетку, paylines, payout, новый баланс и состояние Free Spins.
- Клиент проигрывает полную вертикальную прокрутку барабанов с разгоном, инерционным торможением и staged stop: левый → центральный → правый.
- Payline, payout и изменение баланса показываются только после подтверждённой остановки; клиент не генерирует RNG и не исправляет серверный результат.
- Первый каркас поддерживает пять Free Spins с отдельным серверным исходом каждого вращения.
- Бонусная мини-игра временно остаётся заглушкой и вынесена в отдельную переделку после приёмки Slot v2.

### Hold’em v1 — серверный игровой процесс

**Статус:** утверждён владельцем 13.10.2026 (issue #53). Код пишется по этому разделу; изменения — новым
решением владельца.

Утверждено владельцем (13.10.2026, #53):

- Два режима: **против бота** (серверный соперник, играть можно сразу) и **против живого игрока**.
- Столы с входом **100 / 500 / 1 000 JOKERGEM**, одинаковые в обоих режимах; список столов будет
  дополняться отдельным решением.
- Живой соперник, который не сделал ход за **20 секунд**, теряет ход автоматически.

Правила раздачи:

- Один стол — одна раздача heads-up по `packages/domain` (`create_heads_up_room`, `apply_holdem_action`,
  `settle_holdem`). У обоих мест одинаковый стек, равный входу стола, поэтому ответ на любую ставку всегда
  покрывается, и побочные банки не нужны. Новая раздача — новый вход.
- Блайнды — 5 % и 10 % входа (100 → 5/10, 500 → 25/50, 1 000 → 50/100), то есть 10 больших
  блайндов на стек — короткие быстрые раздачи. Минимальный рейз — как в domain: текущая ставка плюс
  большой блайнд.
- Ограничение domain: ставка «всё» (all-in) возможна, только если остаток стека не меньше минимального
  рейза; отдельного действия all-in в v1 нет.
- При тайм-ауте живого соперника сервер делает check, если он разрешён, иначе fold. В режиме
  против бота тайм-аута у игрока нет: раздача ждёт его, состояние хранится на сервере.
- Поиск живого соперника — очередь по столу; если за 60 секунд соперник не найден, поиск
  отменяется, вход не списывается.

Экономика и ledger:

- Вход списывается через `WalletService` одной операцией `game_stake` в момент начала раздачи (оба места
  заняты); выплата — `game_payout` на итоговый стек плюс доля банка. Каждая операция с idempotency key от
  `action_id`.
- Деление банка при ничьей — целочисленное, как в `settle_holdem`.
- Бот играет «от дома» — его вход не берётся ни с чьего кошелька, а выигрыш игрока у бота
  создаёт Jokergem так же, как выплата в Slot. Для оценки этого перед запуском нужен Monte Carlo
  «игрок против бота» с ожидаемым результатом игрока за раздачу на каждом столе.

Честность и скрытые данные:

- Исход определяет только сервер; боевой RNG — `SystemRandomSource`.
- Колода и закрытые карты обоих мест — только в `private_state_json`. Каждый игрок получает в снимке и
  событиях только свои закрытые карты; карты соперника открываются только на шоудауне, при fold — никогда.
  Это требует снимка и событий **по месту игрока**, а не одного общего публичного состояния комнаты.
- Бот решает на сервере и видит только свои карты и общий борд — не карты игрока и не колоду. Случайность
  бота — тоже `SystemRandomSource`.
- Повтор действия, две одновременные ставки и старый `state_version` не меняют баланс дважды
  (как в Slot и Blackjack).

Интерфейс и дизайн:

- Интерфейс Hold’em — отдельная задача после серверной части: столы, поиск соперника, таймер хода, раскрытие
  борда по улицам, объяснение итога. Визуальное направление комнаты утверждается отдельно, как Deck A у
  Blackjack; до этого используются нейтральные карты и CSS-примитивы.

Соперник-бот (решение владельца 13.10.2026, превью — PR #63):

- В каждой раздаче против бота соперник — герой серий RGG из пула стола: 1 000 — легенды, 500 — капитаны,
  100 — улица (состав пулов — `assets/design/holdem-rgg/sources.json`).
- Героя выбирает сервер «мешком»: без повторов, пока игрок не встретит весь пул стола; затем пул
  перемешивается заново. Случайность — `SystemRandomSource`; код героя — в снимке раздачи и в истории.
- Герой — только оформление: имя, портрет, реплики. Стратегия бота задаётся столом, а не героем.
- В живом режиме вместо героя показывается аватар Telegram соперника.

Вне v1: больше двух мест, серия раздач за одним столом, турниры, чат за столом, побочные банки.

### Hold’em PvP — профиль соперника (#81)

**Статус:** утверждено владельцем 14.10.2026 в сессии Codex после объяснения схемы: «Делай».
Исполнитель Codex, ветка `codex/holdem-opponent-profile`. Отдельная задача после #75;
текущее нейтральное имя «Живой игрок» остаётся до выпуска этого изменения.

Утверждённый объём и источник данных:

- Ник — только `User.username`, обновляемый из проверенного Telegram initData;
  отображение `@username`, при отсутствии — «Живой игрок». `display_name`, внутренние
  user ID и Telegram ID не добавляются в публичный профиль.
- Аватар — первая доступная фотография через Telegram Bot API `getUserProfilePhotos`
  (`limit=1`), затем `getFile` и загрузка самой маленькой версии фото. API использует
  уже настроенный BOT_TOKEN; новых секретов, сервисов и миграций нет. При отсутствии
  фото или недоступности источника — нейтральная иконка. Не использовать произвольные
  `photo_url` клиента или `initDataUnsafe`; фото не является доказательством личности.
- Получение фото выполняется отдельно от snapshot, WS, действий и settlement,
  чтобы сбой Telegram не задерживал игру и не влиял на баланс или таймер хода.

Контракт и доступ:

- Seat-specific `public_state.opponent_profile` имеет поля `nickname` и `avatar_path`.
  Профиль есть только для найденного живого соперника; ожидание и режим бота — `null`.
  Один проектор используется HTTP и WS; поля закрытых карт и логика showdown не меняются.
  Ник отражает последнее подтверждённое значение в User, а не исторический ник события.
- Относительный путь `/api/v1/rooms/{room_id}/opponent-avatar` разрешён только после
  Telegram-авторизации и проверки членства в конкретной Hold’em PvP-комнате с двумя
  местами. Цель определяется по противоположному месту; endpoint не принимает ID или URL.
  Проверка доступа выполняется перед чтением кэша при каждом запросе.
- API возвращает байты JPEG/PNG, `Cache-Control: no-store` и
  `X-Content-Type-Options: nosniff`; SVG/HTML и неподдерживаемые данные отклоняются.
  Фото отсутствует — 204; временный сбой источника — 503; локальный лимит — 429
  с Retry-After. Ответы и логи не раскрывают token, file path/URL или профиль источника.
- Mini App получает фото через авторизованный fetch, создаёт локальный blob URL и
  освобождает его при смене комнаты/уходе. Заголовок initData не помещается в URL.
  В DEMO запросов профиля нет. Ошибки фото сохраняют нейтральную иконку; reconnect
  допускает новый запрос, без циклических фоновых попыток. Новые поля необязательны
  для совместимости со старым API. Игра и герой-бот сохраняют прежнее поведение.

Хранение и лимиты (утверждённые значения проекта, не ограничения Telegram):

- Только память единственного API-процесса: LRU до 64 профилей, максимум 256 KiB
  на фото (до 16 MiB суммарно). Положительный TTL 1 час, отсутствие фото 5 минут,
  временный сбой 30 секунд. Перезапуск очищает кэш; фото, file ID и URL не сохраняются
  в User, room state, events, ledger, Redis или на диск. Обновление фото видно после TTL.
- До 30 запросов avatar endpoint за минуту на авторизованного пользователя; до 60
  новых загрузок за минуту на весь API, максимум две одновременно. Совпадающие
  загрузки одного соперника объединяются. Учёт лимитов также ограничен по памяти.
- Общий deadline цепочки Telegram — 5 секунд, автоматических повторов нет;
  upstream 429 соблюдает Retry-After. Размер JSON-ответов и streaming download
  ограничен; перенаправления запрещены, origin только `https://api.telegram.org`.
  Путь файла валидируется до загрузки; сторонние хосты, абсолютные пути, query,
  traversal и userinfo не допускаются. HTTP exception/URL никогда не печатаются.

Проверки и выпуск:

- Backend: профили каждого места в HTTP/WS, waiting/bot, ник отсутствует/удалён,
  чужая комната и неавторизованный запрос, отсутствие ID/display_name/закрытых карт;
  mocked Telegram success/no-photo/timeout/429/malformed response/oversize/redirect,
  TTL, ограничение кэша, лимиты и объединение запросов. Live Telegram вызовы в тестах
  не нужны; настоящие токены/профили в fixtures запрещены.
- Frontend: парсинг optional полей, отображение ника, успешный blob и fallback,
  reconnect/смена комнаты/освобождение URL, DEMO без запросов. Проверки check/test/build
  и Playwright; ручная приёмка двумя аккаунтами в Telegram после серверного выпуска.
- Обновить ProjectLog/ChangeLog; PR включает API service/router, контракты и клиент,
  тесты и документацию. Domain/RNG/ledger, схема БД, production compose и стратегия
  бота не меняются. Нужен исходящий HTTPS API→Telegram; httpx уже входит в зависимости.
  Merge/Pages и серверный deploy — отдельные действия по поручению владельца.

Источники протокола: [Telegram Bot API](https://core.telegram.org/bots/api#getuserprofilephotos),
[getFile](https://core.telegram.org/bots/api#getfile),
[проверка initData](https://core.telegram.org/bots/webapps#validating-data-received-via-the-mini-app).

### Рейтинг v1 — недельный результат

Утверждено владельцем 13.10.2026 (#52): топ-15 по чистому игровому результату
(сумма `game_stake` и `game_payout` в ledger) за текущую календарную неделю МСК:

### Slot Siege v1 — ротация операций (#76)

Утверждено владельцем в задании #76; старт цикла уточнён в сессии Codex 13.10.2026:
**19.10.2026, понедельник 00:00 МСК**. До старта показывается «Ледяной рассвет»;
первая смена на «Красный сигнал» — 26.10.2026 00:00 МСК. Далее каждые 7 дней:
op1 → op2 → op3 → op4 → op1. Составы из утверждённого `assets/design/slot-r6/lineups.js`
упаковываются в domain JSON; W всегда Tachanka. Ленты, выплаты и ruleset_version не меняются.

Ивент `arena` перекрывает календарную операцию в полуоткрытом интервале [start, end)
через `SLOT_EVENT_OPERATION_ID`, `SLOT_EVENT_STARTS_AT`, `SLOT_EVENT_ENDS_AT` (aware ISO 8601).
Все три поля обязательны вместе; start < end, неизвестный код/naive time — ошибка конфигурации
при старте API. По окончании возвращается календарная операция, цикл не сдвигается.
Автоматического включения по условию сообщества/админ UI здесь нет.

В snapshot и spin result/event: `operation_id`, `next_operation_id`, `operation_changes_at`.
Операция спина фиксируется до генерации сетки/ожидания ledger и сохраняется с результатом;
replay возвращает прежние поля даже после границы недели/ивента. Snapshot сообщает текущую
операцию для следующего спина, а `last_result` сохраняет операцию завершённого спина;
UI до конца его показа использует operation_id результата. Следующая операция и срок
позволяют UI показать анонс за 24 часа. Skeleton-комнаты не получают метаданные Siege.

## Economy v0.1

- Рабочее название валюты: **Jokergem**, код `JOKERGEM`; название остаётся сменным без миграции балансов.
- Хранятся целые единицы, не деньги и не финансовые значения.
- Стартовая выдача: `1 000 JOKERGEM` один раз.
- Ежедневная выдача: `250 JOKERGEM` раз в 24 часа.
- Relief-грант: `300 JOKERGEM`, если баланс ниже `50`, не чаще одного раза в 72 часа.
- Нет покупки, вывода, обмена, призов, Stars и P2P-переводов.
- Каждая мутация имеет `X-Request-ID`/idempotency key и append-only ledger.

Стартовые числа — техническая baseline-конфигурация для закрытого теста, а не обещание игрокам и не решение о монетизации.

## Scope

- Привязка бота к одному выбранному чату комментариев.
- `/start`, `/casino`, `/balance`, `/top`, `/help` и кнопка входа в Mini App.
- Проверка сырого Telegram `initData` на API; `initDataUnsafe` не является trust boundary.
- Профиль, баланс, журнал операций, комнаты, snapshot/event и восстановление после reconnect.
- Роли администраторов, лимиты, аудит и редкие анонсы только отдельным разрешённым действием.
- PostgreSQL как источник истины, Redis для locks/presence/pub-sub, SvelteKit для интерфейса и motion.

## Out of scope

- Реальные деньги, криптовалюта, вывод, обмен, платные шансы и продажа игровой валюты.
- Stars до отдельного BuildSpec, юридической проверки, `/paysupport`, возвратов и журнала платежей.
- Сбор полной истории чатов, RAG, анализ токсичности и фоновые массовые рассылки.
- Мультичатность до стабилизации одного сообщества.
- Финальные персонажи и тематические ассеты до прохождения domain/API/room тестов и приёмки визуального направления.

## Acceptance criteria

- Пользователь открывает Mini App из Telegram и получает серверно-проверенный профиль.
- Баланс не вычисляется и не хранится как источник истины в браузере.
- Повтор tap/retry и две конкурентные ставки не создают второе списание или вторую выплату.
- Старый `state_version` отклоняется; reconnect читает durable snapshot и не дублирует action.
- Slot, Blackjack и Hold’em проходят доменные переходы, integer payout/tie-split проверки и воспроизводимые симуляции.
- UI сохраняет legal actions, объяснение результата, focus states, safe-area padding и readable state при reduced motion.
- Slot UI показывает полную прокрутку барабанов, подтверждённую сетку, payout highlight и Free Spins без подмены outcome на клиенте.
- Бот не пишет в чат без действия пользователя или явно включённого admin announcement.
- Секреты не попадают в source, fixtures, logs, Docker image layers или тестовые ответы.
- CI выполняет Python lint/tests, PostgreSQL integration tests, Mini App check/test/build и три Monte Carlo reports.

## Remaining product decisions before public launch

1. Утвердить финальный RTP/лимиты для каждой тематической версии поверх skeleton rulesets.
2. Утвердить финальные тематические ассеты, персонажей, звук и правила публичного шаринга.
3. Зафиксировать владельцев, модераторов, целевой чат, FAQ и поддержку.
4. Провести ручную приёмку iOS, Android и Telegram Desktop на staging.
5. Провести юридический/security review перед любым платным контуром.

Визуальный motion-слой передаётся в Command Code только по [зафиксированному workflow](../docs/Command-Code-Workflow.md), с моделью, effort, ограничением файлов и тестами.

Для production arena нужно отдельно передать три SLOT_EVENT_* переменные в environment контейнера API: текущий docker-compose.prod.yml их не передаёт, одной записи в host .env недостаточно. Compose не входит в allowlist #76 и не менялся. Для календарной ротации новые env не нужны.
