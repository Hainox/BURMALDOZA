# Правила Claude Code для BURMALDOZA

## Обязательный контекст

Перед существенной работой читай документы строго в таком порядке:

1. `dev/Vision.md` — цель продукта и неизменные ограничения.
2. `dev/BuildSpec.md` — утверждённый scope и критерии приёмки.
3. `dev/ProjectLog.md` — предыдущие решения, текущий статус и открытые задачи.
4. `docs/Command-Code-Workflow.md` и связанное issue — правила handoff для выбранного исполнителя.

Не выводи новые продуктовые требования из черновиков, картинок или старых записей журнала. При конфликте следуй актуальному решению владельца и явно отметь, что именно нужно согласовать.

## Границы изменений

- Codex ведёт архитектуру и интеграцию; domain, RNG, ledger, API-контракты, безопасность, миграции и deployment меняй только по задаче с явным scope и утверждённым BuildSpec.
- На один набор файлов назначается один implementer. Не редактируй файлы, одновременно назначенные Codex или Command Code; используй отдельную ветку/worktree.
- Начинай с `git status` и сохрани все изменения пользователя. Не сбрасывай, не очищай и не перезаписывай посторонние файлы.
- Не включай секреты, `.env`, токены, приватные данные, реальные ключи или их значения в prompts, вывод, фикстуры, примеры и коммиты. Не публикуй сообщения/файлы и не меняй доступ без явного разрешения владельца.
- Не открывай `.env`, credential-файлы и секретные конфигурации в сессии: Claude Code может хранить prompts, прочитанные файлы и результаты инструментов в локальных текстовых transcripts. Передавай только необходимый безопасный контекст и не коммить transcript/log/cache.
- Не используй `--dangerously-skip-permissions`, force-push, merge или deploy вне явного разрешения текущей задачи.
- Claude Pro используется через официальный Claude Code login. Перед каждой рабочей сессией проверь `/status`; если обнаружен `ANTHROPIC_API_KEY` или неясно, что сессия использует Pro, остановись, не раскрывая значение ключа.
- Не включай платные usage credits, API billing или auto-reload без отдельного решения владельца. Claude.ai и Claude Code расходуют общую квоту; проверяй Settings → Usage и `/status`, не фиксируй изменяемые оценки лимитов.

## Проверка и отчёт

- Ограничивай diff указанными файлами и выполняй релевантные проектные проверки. Для UI укажи точные ручные проверки, если автоматизированного сценария недостаточно.
- Если задача — review, работай read-only/Plan Mode: не редактируй файлы и верни только findings с точными путями и строками.
- После значимого изменения обнови `dev/ProjectLog.md`. Обновляй `ChangeLog.md` только для пользовательских, deploy- или compatibility-изменений.
- В отчёте перечисли изменённые файлы, команды и результаты проверок, остаточные риски и commit/branch. Не называй проверку пройденной без фактического результата.
