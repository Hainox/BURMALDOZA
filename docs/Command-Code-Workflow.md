# Рабочий процесс Codex ↔ Claude Code ↔ Command Code

**Дата фиксации:** 24 сентября 2026 года
**Назначение:** выбирать одного исполнителя на изолированную задачу, заранее фиксировать границы, проверки и способ авторизации, а затем интегрировать результат через Codex.

## Роли инструментов

| Инструмент | Основная роль | Граница ответственности |
| --- | --- | --- |
| Codex | Архитектура, планирование, сервер/domain/RNG/ledger/API, безопасность, интеграция и финальная проверка | Источник решений по контрактам и интегратор результата; критические изменения идут только по утверждённому BuildSpec. |
| Claude Code через Claude Pro | Независимый read-only review готового diff; документация, тесты и небольшие самостоятельные изменения с точным allowlist | Запускать в отдельной ветке/worktree. Не делить одни файлы с Codex или CCode. Для текущей UI handoff-задачи #6 не заменяет CCode без отдельного решения. |
| Command Code (CCode) | Основной назначенный исполнитель визуальных UI/motion handoff-задач | Работает по закреплённой модели и effort. Не меняет domain, RNG, ledger или API-контракты, если это отдельно не разрешено. |

## Модели и effort для каждой задачи

В каждом issue, handoff, запуске исполнителя и итоговом отчёте указывай отдельной строкой **инструмент, точную модель и effort**. Не полагайся на молчаливый default и не копируй модель из предыдущей задачи без проверки. Если точная модель или effort не зафиксированы платформой, сначала выбери их явно; если это невозможно — отметь блокером, не придумывай значение.

| Инструмент / тип задачи | Модель | Effort | Как зафиксировать |
| --- | --- | --- | --- |
| Codex: обычная реализация, интеграция и review | `gpt-6-sol` | `high` | Передавать явными `model` и `thinking` при создании/маршрутизации задачи; сохранять пару в handoff и отчёте. |
| Codex: межсистемная архитектура, безопасность или критичный финальный review | `gpt-6-astra` | `xhigh` | Использовать только когда задача действительно требует усиленного анализа; явно передавать `model` и `thinking`. |
| Claude Code через Pro: реализация или review | Точная модель, выбранная и показанная в `/model` или `/status` | `high` | Передавать явные `--model <model>` и `--effort high`; в отчёте указать выбранную модель и подтвердить Pro-вход через `/status`. |
| Claude Code через Pro: узкая документационная задача | Точная модель, выбранная и показанная в `/model` или `/status` | `medium` | Передавать явные `--model <model>` и `--effort medium`; в отчёте указать модель и Pro-вход. |
| Command Code (CCode): утверждённые UI/motion handoff-задачи | `meta/muse-spark-1.3-contributor` | `high` | Передавать пару в каждой задаче и issue; не менять без обновления handoff. |

Если основной маршрут недоступен, сначала укажи в задаче фактически выбранную замену вместе с effort и только затем запускай её. Не называй провайдера моделью: нужны точный model ID и уровень effort.

## Параллельность: когда вместе, когда по очереди

Параллельная работа допустима, если одновременно выполнены все условия:

- продуктовый scope и API/данные-контракты уже зафиксированы в `dev/BuildSpec.md` или отдельной принятой спецификации;
- исполнители получили непересекающиеся списки файлов и отдельные ветки/worktree от указанной базы;
- у каждого handoff есть владелец интеграции, acceptance criteria, проверки, точные модель и effort;
- параллельные задачи не меняют один и тот же файл и не ждут результат друг друга.

Read-only аудит, исследование и дизайн можно делать одновременно, если выводы не превращаются в параллельные правки одних файлов. Для каждого файла назначается один implementer; другой инструмент может в это время только читать и готовить findings.

Зависимые изменения выполняются по очереди:

1. Codex проверяет Vision/BuildSpec/ProjectLog, фиксирует продуктовый контракт и границы задачи.
2. Один назначенный исполнитель делает серверный или доменный срез и тесты; Claude Code может быть implementer на узком allowlist либо read-only reviewer, но не второй писатель тех же файлов.
3. Codex проверяет контракт, тесты и интеграцию; только после этого контракт считается стабильным для UI.
4. CCode реализует UI/motion по принятому контракту и отдельному handoff. Черновой UI на замороженных mock-данных можно делать параллельно только в отдельном компоненте; до интеграции Codex сверяет его с реальным контрактом.
5. Codex выполняет сквозную проверку и системную интеграцию; Claude Code может отдельно провести read-only review после остановки изменений.
6. Владелец принимает решение о merge и deploy.

Если задача меняет общий маршрут вроде `apps/miniapp/src/routes/+page.svelte`, её нельзя выдавать двум исполнителям параллельно. Сначала завершается текущий handoff и фиксируется его PR, потом начинается следующий. Например, issue #11 ожидает завершения Blackjack UI issue #6, потому что обе задачи затрагивают `+page.svelte`; это очередь по зависимости, а не запрет на параллельные независимые задачи.

Срез на 24 сентября 2026 года: Claude Code подготовил ограниченную реализацию по PR #10, Codex завершил аудит и открыл stacked correction PR #12; CCode issue #6 ждёт merge визуального checkpoint PR #8; wallet UI issue #11 ждёт принятого серверного изменения PR #10/#12 и завершения issue #6. Обновляй этот снимок после прохождения зависимостей; не запускай конкурирующие правки одного файла ради ускорения.

## Маршрутизация моделей Command Code

| Задача | Модель | Effort | Правило |
| --- | --- | --- | --- |
| Основная реализация UI и motion | `meta/muse-spark-1.3-contributor` | `high` | Основной выбор для самостоятельной работы в репозитории. |
| Архитектурная проверка и финальный review | `gpt-5.6-sol` | `high` | Использовать для критичных контрактов, сложных merge и финального аудита. |
| Небольшие независимые правки | `deepseek/deepseek-v4.1-flash` | `medium` | Быстрые локальные задачи; не делать единственным маршрутом проекта. |
| Резервный быстрый исполнитель | `z-ai/glm-5.3-flash` | `high` | Применять при недоступности основного исполнителя или для второго прохода. |
| Локальная бесплатная проверка | `qwen3-8b-local` | `low` / `/no_think` | Форматирование, чтение diff, простые проверки без сложного проектирования. |

Идентификатор модели и effort указываются в каждом handoff явно. DeepSeek не используется как единственная дорога: ранее для него уже встречался `429`, поэтому у задачи всегда должен быть запасной маршрут.

## Расход квоты Command Code

- перед дорогой задачей проверить `/usage`;
- не включать автоматический top-up без отдельного решения владельца;
- сильную модель оставлять для архитектуры, motion-критичных задач и финального review;
- отправлять в сессию только нужный контекст, без несвязанных старых диалогов;
- задача должна иметь ограниченную область файлов и проверяемый acceptance checklist.

Эти правила относятся к квоте Command Code. Она не является квотой Claude Pro и не объединена с ней.

## Claude Code через Claude Pro

- Claude Code запускается как отдельный официальный CLI; Claude Pro подключается входом в тот же Claude-аккаунт. Используй подписку через официальный Claude Code login; не передавай Claude-учётные данные в Command Code и не считай подписку API-ключом.
- Перед каждой рабочей сессией проверь в Claude Code через `/status`, что выбран вход через план Claude, а не API-ключ, и видна ожидаемая модель. Модели выбираются в `/model`; записывай фактически выбранную модель, не закрепляй в документации изменяемые model ID и не предполагай доступность Opus в Pro.
- Лимиты Claude Pro общие для Claude.ai и Claude Code, включая IDE-интеграцию; расход зависит от контекста и задачи. Перед большой сессией проверяй Claude **Settings → Usage** и `/status`. Не обещай и не хардкодь число запросов на сессию.
- `ANTHROPIC_API_KEY`, если он задан в окружении Claude Code, может переключить авторизацию на API-биллинг вместо подписки. До запуска проверяй, что задача использует Pro-вход; не выводи и не копируй значение ключа. Если авторизация неоднозначна — остановись и уточни её у владельца.
- Claude Code сохраняет prompts, прочитанные файлы и результаты инструментов в локальные plain-text transcripts. Поэтому не открывай `.env`, credential-файлы или другие секреты в сессии; передай только нужный безопасный контекст. Не добавляй transcript/log/cache каталоги в репозиторий.
- Не включай usage credits/auto-reload, не выбирай Claude Console pay-as-you-go и не принимай предложение перейти на платные API-кредиты без отдельного явного решения владельца. Если квота исчерпана — остановись до её обновления или согласованного маршрута.
- Используй Claude Pro для узких задач с релевантными файлами и одним компактным контекстом. Для большой кодовой базы сначала дай точный список файлов и критерии, а не запускай обзор всего репозитория. Не запускай параллельные сессии для одной задачи: они делят общую квоту и повышают риск конфликтующих правок.
- Оставляй штатные запросы разрешений включёнными. Не используй `--dangerously-skip-permissions` и не включай обход проверок.

### Последовательность работы с Claude Code

1. Прочитай `dev/Vision.md`, `dev/BuildSpec.md`, затем `dev/ProjectLog.md`; для handoff дополнительно прочитай этот документ и точное issue/acceptance.
2. Назначь одного исполнителя на изменяемые файлы. Для Claude Code создай отдельную ветку/worktree от указанной актуальной базы; параллельно допускаются только независимые задачи с непересекающимися файлами. Не работай в checkout с чужими изменениями.
3. До запуска зафиксируй точные модель и effort. Для Claude Code передай `--model <model из /model>` и `--effort high` для реализации/review либо `--effort medium` для узкой документации; через `/status` подтверди Claude Pro и отсутствие API-авторизации. Затем передай минимально достаточный контекст, allowlist, запреты и команды проверок.
4. Claude Code показывает план/дифф и запускает только нужные проверки. Исполнитель возвращает изменённые файлы, команды и результаты, незакрытые дефекты и точный commit/branch.
5. Для задания на review явно скажи «read-only: не редактировать», используй Plan Mode и верни findings с путями/строками. Для implementation Codex независимо сверяет diff с BuildSpec, запускает нужные тесты и интегрирует результат. Коммит/публикация выполняются только в пределах разрешения на текущую задачу; force-push запрещён.
6. После значимого изменения обнови `dev/ProjectLog.md`; `ChangeLog.md` меняй только при пользовательском, deploy- или compatibility-эффекте.

## Пример ограниченного handoff для Slot v2

```text
Репозиторий: Hainox/BURMALDOZA
Ветка: ccode/slot-v2-motion
Модель: meta/muse-spark-1.3-contributor
Effort: high

Собери визуальный слой комнаты Slot v2. Работай только в разрешённых файлах:
- apps/miniapp/src/lib/rooms/SlotRoom.svelte;
- slot-only компоненты и стили рядом с ним.

Не меняй domain, RNG, ledger, API contracts и server fixtures. Не подменяй
серверный SlotOutcome локальным результатом.

Acceptance criteria:
- барабаны прокручиваются полной вертикальной лентой;
- есть разгон, инерционное торможение и последовательная остановка левый → центр → правый;
- итоговая сетка берётся из подтверждённого результата;
- выигрышная линия и выплата подсвечиваются после остановки;
- есть визуальное состояние Free Spins и счётчик вращений;
- reduced-motion сохраняет смысловую последовательность;
- Playwright проверяет запуск, остановку и стабильный финальный результат.
```
