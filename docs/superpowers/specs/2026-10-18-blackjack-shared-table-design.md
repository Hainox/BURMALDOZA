# Blackjack: отдельный общий стол для 1–3 игроков

Статус: продуктовые правила согласованы владельцем 18.10.2026 в #116.
План реализации — [рядом](../plans/2026-10-18-blackjack-shared-table.md).
Технические решения ниже предлагаются для реализации и ревью плана; код ещё не изменён.

## Цель и режимы

В Blackjack GFL перед входом выбирается «С ботом» или «Общий стол».
«С ботом» сохраняет текущую одиночную игру против дилера, старые комнаты и DEMO.
Общий стол — 1–3 реальных игрока против одного серверного дилера, с отдельными
руками, ставками и расчётом каждого игрока. Игроки не играют друг против друга.
Режимы не переключаются внутри уже созданной комнаты.

## Согласованный игровой цикл

1. Игроки занимают до трёх мест; каждый выбирает ставку и нажимает «Готов».
2. Создатель запускает раздачу, когда все занявшие места готовы. Можно начать
   одному или вдвоём, ждать заполнения необязательно. Автоматических ставок нет.
3. Общая колода, две открытые карты каждому и карта дилера рубашкой вверх.
4. Ходы по порядку мест: Hit / Stand / Double. На каждое решение 20 секунд;
   истечение срока означает Stand. Естественный Blackjack и перебор пропускаются.
5. После завершения игроков дилер доигрывает один раз. Каждый результат отдельно
   сравнивается с дилером; деньги проходят только через WalletService.
6. Следующая раздача требует новой готовности и явного старта.

Ставки и выплаты сохраняются: исходная ставка 25–1 000 000 JG; Blackjack 3:2
с существующим целочисленным округлением; обычная победа 1:1, ничья возвращает
ставку. Дилер стоит на soft 17. Double требует доплату, одну карту и завершает
ход; первоначальный потолок ставки не ограничивает удвоенную сумму задним числом.
Split, Insurance и новые бонусы не добавляются.

## Присоединение, выход и восстановление

Предложенный вход v1: «Создать стол» / «Войти по коду»; код — UUID комнаты.
Это адрес общего стола, не секрет и не замена Telegram-авторизации. Публичный
каталог, наблюдатели и автоматический matchmaking не входят в эту версию.
При повторном входе участник получает своё место, а не занимает второе.

Вход в свободное место во время раздачи разрешён с ожиданием следующей. Такой
игрок не получает карт, не ставит и не меняет текущую очередь. Занятый участником
раздачи слот не освобождается до расчёта: максимум три места включает ушедших.
Вышедший во время раздачи остаётся в текущем расчёте и заканчивает по тайм-ауту;
выход не возвращает ставку. Разрыв WS сам по себе не означает выход со стола.
После расчёта уходящие удаляются. Если создатель ушёл, управление переходит
оставшемуся участнику с минимальным номером места; пустой стол закрывается
после выполнения всех расчётов.

Переподключение восстанавливает место, руку, очередь и абсолютный UTC deadline.
Рестарт API не меняет колоду, карты, ставки и срок. Просроченный ход завершает
серверный обработчик, а не клиент. Нажатие после deadline сначала отклоняется
или получает уже обновлённый snapshot; оно не может выиграть гонку с тайм-аутом.

## Архитектура и совместимость

- Общий стол: `game_type=blackjack`, `mode=table`, ruleset `blackjack-gfl-table-1`.
  Текущий solo-dispatch сохраняется для существующих режимов и версий.
- Новый чистый domain-модуль `games/blackjack_table.py` хранит общую колоду,
  дилера, до трёх рук, порядок хода и результаты. Использует Card, hand_value,
  BlackjackRules и RNG из текущих модулей. Не вызывает одиночный dealer resolution
  после каждого игрока и не перетасовывает использованные карты в середине раздачи.
- Новый `BlackjackTableService` по образцу HoldemService владеет lobby/membership,
  транзакциями, дедлайнами, проекцией, action replay и публикацией после commit.
  RoomService только направляет table-комнаты в этот сервис.
- Используются GameRoom (JSON + private JSON + deadline), GamePlayer и GameRound.
  Миграция не планируется: нынешняя схема уже хранит три уникальных места,
  приватный state и общий результат. Если этого недостаточно, изменение схемы
  отдельно обосновать и согласовать, а не прятать в реализацию.
- API остаётся с одним worker. Новый tick общего стола работает независимо от
  Hold’em; ошибка одной комнаты не останавливает обработку остальных.

## API и состояние

Предлагаемые интерфейсы:
- POST /api/v1/rooms: Blackjack `mode=table`, обязательный UUID `action_id`
  для идемпотентного создания. Без buy_in: деньги списываются только на старте.
- POST /api/v1/rooms/{id}/join: UUID action_id; атомарно занять место или вернуть
  прежнее. Проверить, что это Blackjack table. Четвёртому — конфликт без мутаций.
- Общий /actions: `ready {bet}`, `unready`, `start`, `hit`, `stand`, `double`,
  `leave`; action_id + expected_state_version. Чужой ход запрещён, start только
  создателю. Повтор action_id связан с actor и payload, несовпадение — конфликт.
- Snapshot и WS имеют одну проекцию: phase, round_id, host_seat, viewer_seat,
  players (seat, nickname, cards, total, bet, status, ready, outcome), dealer,
  active_seat, turn_deadline, доступные текущему пользователю legal_actions.
  Баланс получает только его владелец. Ники из разрешённого User.username,
  иначе «Игрок без ника»; внутренние user ID, Telegram ID и реальные имена
  других участников не публикуются. Фото участников не входят в scope.
- Public dealer содержит видимые карты и `{hidden: true}` вместо закрытой;
  total/результат/лог события не раскрывают закрытую карту косвенно. Колода и
  полная рука дилера только в private_state_json до раскрытия.
- При settled разрешена готовность следующего раунда; прежние итоги видны до
  нового start. Readiness сбрасывается на старте, старые result не озвучиваются
  повторно после resync. Проекция legal_actions зависит от места, не от UI.

Все HTTP и WS пути используют существующую Telegram auth и ограничения API;
добавленный join получает те же применимые лимиты. UUID стола не даёт права
читать snapshot без membership. Leaving participant после выхода не может
читать обновления, но сервер сохраняет его для расчёта.

## Транзакции и идемпотентность

Порядок: room row lock → кошельки по возрастанию user_id → изменения ledger.
На start все ставки проверяются и списываются в одной транзакции; недостаток
средств у любого откатывает весь start, карты и события тоже не фиксируются.
Кнопка ready денег не резервирует. Double блокирует кошелёк и доплату атомарно
с картой; отказ не меняет колоду или очередь. Не блокировать кошельки в порядке
мест: у игроков возможны другие комнаты и конкурентные операции.

Для start/double/settlement нужны разные детерминированные UUID ключи на
(room, round, seat, этап), привязанные к реальному action/round ID. Ключ одного
игрока никогда не становится ключом другого. Ставки и выплаты имеют существующие
причины game_stake/game_payout и общий reference round; админские операции не
используются. Все выплаты раздачи фиксируются одной транзакцией. Ошибка последней
выплаты не оставляет первых игроков рассчитанными. Повтор расчёта возвращает
durable прежний итог без повторного RNG или средств. Ledger-реализацию не менять.

Tick блокирует комнату, повторно проверяет deadline и версию, создаёт stable
UUID тайм-аута из room/version/deadline, делает Stand и коммитит. Параллельный
ручной ход не может примениться к той же версии. Каждый новый выбор получает
свои 20 секунд; после рестарта не продлевать истёкший срок.

## Проверки и выпуск

- Domain: 1/2/3 руки, уникальность общей колоды, естественные Blackjack/bust,
  soft 17, Double, нечётные ставки, независимые итоги против одного дилера.
- PostgreSQL: конкурентный join, ready/start/leave, недостаток средств и rollback,
  конфликт action_id, double retry, атомарный расчёт, timeout vs action и рестарт.
- Проекция HTTP/WS: доступ участников, выход, скрытая карта/колода, чужой баланс,
  поздний вход и восстановление; solo-контракты и старые комнаты сохраняются.
- UI/E2E: выбор обоих режимов, три сессии и четвёртый отказ, очередь, таймер,
  ready/reset, результат, reconnect, reduced motion, 320/390/1440 px.
- DEMO не создаёт фиктивных онлайн-игроков: solo доступен, общий стол явно требует
  подключения к серверу и Telegram. Режим нельзя незаметно заменить демо.
- Ruff/pytest с PostgreSQL+Redis, frontend check/test/build/E2E и Docker CI.
  Ручная приёмка 3 аккаунтами после отдельного согласованного выпуска.
- Merge и server deploy — отдельные действия. PR #117 не включать в эту ветку.
