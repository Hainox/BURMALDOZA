## Найденные проблемы

### 1. Высокая — у нового игрока в live-режиме баланс 0 и нет способа его пополнить — ✅ исправлено (сервер), кнопки в Mini App — за CCode

`WalletService.claim_welcome_grant` (1 000) и `claim_relief_grant` (300) реализованы и покрыты
тестами, но ни один HTTP-маршрут, команда бота или экран Mini App их не вызывает. Единственный
открытый бонус — `POST /api/v1/wallet/daily-bonus/claim`, но Mini App-клиент (`apps/miniapp/src/lib/api/client.ts`)
его тоже не вызывает. Итог: реальный пользователь входит с балансом 0 и получает
«insufficient balance» на первой же ставке. README при этом обещает welcome 1 000.

**Что сделать:** добавить маршруты `POST /wallet/welcome/claim` и `/wallet/relief/claim`
(или выдавать welcome при первом `_upsert_user`), и кнопки/авто-вызов в Mini App.

### 2. Высокая — CORS ломается, если `MINIAPP_URL` содержит путь (случай GitHub Pages) — ✅ исправлено

`apps/api/app/main.py` использует `MINIAPP_URL` как разрешённый origin. Браузер присылает
origin без пути (`https://hainox.github.io`), а для Pages `MINIAPP_URL` —
`https://hainox.github.io/BURMALDOZA/`. Проверено: preflight-запрос получает `400` и без
`Access-Control-Allow-Origin` — live-режим с Pages не заработает. Та же переменная нужна
боту как полный URL кнопки, поэтому просто убрать путь нельзя.

**Что сделать:** вычислять origin из `MINIAPP_URL` (`scheme://host[:port]`) или завести
отдельную переменную `CORS_ALLOWED_ORIGINS`; добавить тест с URL-путём.

### 3. Средняя — WebSocket принимает соединение до авторизации без тайм-аута — ✅ исправлено

`routers/rooms.py::room_events` делает `accept()` и ждёт первое сообщение бесконечно.
Кто угодно может держать много «пустых» соединений, каждое держит DB-сессию.

**Что сделать:** обернуть первый `receive_json()` в `asyncio.timeout(5)` и закрывать с 4401.

### 4. Средняя — ключ идемпотентности кошелька не привязан к пользователю — ✅ исправлено

`WalletService._db_replay` ищет операцию только по `idempotency_key`. Если пользователь B
пришлёт `X-Request-ID` пользователя A, он получит результат операции A (баланс A).
Риск невелик — UUID трудно угадать, — но проверка дешёвая.

**Что сделать:** в `_db_replay` сравнивать `operation.wallet_id` с текущим кошельком и
отвечать ошибкой при несовпадении.

### 5. Низкая — `_db_get_or_create_wallet` создаёт «фейкового» пользователя

Если `users.id` не найден, создаётся `User(id=user_id, telegram_user_id=user_id)`. Явная вставка
`id` не двигает PostgreSQL-sequence (будущий конфликт PK), а `telegram_user_id` может совпасть
с настоящим аккаунтом. В обычных запросах пользователь уже существует, так что это путь
только для тестов/скриптов — лучше бросать ошибку.

### 6. Низкая — прочее

- Балансы — `Integer` (32 бита, до ~2,1 млрд). Сейчас достаточно, при росте — `BigInteger`.
- `EventBus` работает в памяти одного процесса: при нескольких воркерах uvicorn события не
  дойдут до сокетов на другом воркере (в docstring отмечено; Redis уже есть в стеке).
- Внутренний API бота авторизуется самим `BOT_TOKEN`. Работает, но при утечке один секрет
  даёт и Telegram-бота, и API; лучше отдельный `INTERNAL_API_TOKEN`.
- Hold’em в API принимает действия, но игровой логики на сервере пока нет — ожидаемо для
  текущего этапа, но стоит явно пометить в UI.
- Одновременное создание кошелька для нового пользователя двумя запросами даст
  `IntegrityError` → 500 (редкий случай; решается `INSERT ... ON CONFLICT DO NOTHING`).

**Эксплуатационное решение на 2026-09-24:** пока `EventBus` остаётся локальным для процесса,
production поддерживает один API worker и одну реплику. Наличие Redis в Compose не означает,
что Pub/Sub для игровых событий уже внедрён; для нескольких процессов нужен отдельный
утверждённый проект с анализом отказов и межпроцессными тестами. `Wallet.balance`,
`LedgerEntry.amount_delta` и `LedgerEntry.balance_after` сейчас используют 32-битный
`Integer`: риск переполнения отложен.
Миграцию на `BigInteger` не начинать, пока владелец не утвердит порог и требования к
совместимости данных и API.

## Что сделано хорошо

- Проверка Telegram `initData`: HMAC, `compare_digest`, свежесть, отказ от дублирующихся ключей.
- Ledger: append-only, `SELECT ... FOR UPDATE` на кошельке, CHECK-ограничения на неотрицательный баланс.
- Боевой RNG — `secrets.SystemRandom`; seeded RNG только для тестов/Monte Carlo.
- Колода и hole-card блэкджека хранятся в `private_state_json` и не попадают в публичное состояние.
- Слот отклоняет дубликаты paylines (нельзя умножить выигрыш повтором линии).
- В Mini App нет `{@html}`/`innerHTML` — XSS-поверхность минимальна.
